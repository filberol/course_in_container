# Лаб 2 — harness (для преподавателя)

Скелет автопроверки и защиты к лабораторной «Оркестрация в Kubernetes».
Задание для студента: [`../../Лабораторные/Лаб. 2 Работа с кластерами.md`](../../Лабораторные/Лаб.%202%20Работа%20с%20кластерами.md).

## Модель

Два уровня доверия:

- **Локально у студента** — `make check` на его `kind`-кластере. Тренажёр с мгновенным
  фидбэком. Не доверенный: студент может подделать вывод, обманет только себя.
- **На защите** — `make grade` на машине преподавателя из зафиксированного коммита
  студента. Доверенный прогон: свежий кластер, применяются закоммиченные манифесты,
  повторяются контракты, затем персональные вопросы и вброс сбоя.

Автопроверка — это **ворота допуска**, а не балл. Зелёные ворота = право защищаться.
Балл (0–12) ставится на защите: 3 (ворота + evidence) + 5 (вопросы) + 4 (break-fix).

## Против списывания и GPT

- **Сид от ИСУ** (`seed.py`) привязывает параметры и canary-токен к личности. Копия
  чужой работы несёт чужой токен — контракты падают.
- **Контракты слепы к способу** — проверяется исход, не текст манифеста. Нельзя
  «зашить» ожидаемое решение, значит и Goodhart-оптимизация под тест ограничена.
- **evidence-печать** (`evidence/collect.sh`) сворачивает состояние в хеш; коммит
  фиксирует его во времени.
- GPT выдаёт корректное решение и проходит ворота — это ожидаемо. Понимание ловит
  живой канал: `questions.py` (из его же манифестов) и `breakfix.py` (диагностика
  вживую, ~10 минут, AI за клавиатуру не посадишь).

## Файлы

| Путь | Роль |
| --- | --- |
| `workspace/` | собираемый контейнер-воркспейс: весь инструментарий + DinD + фронт code-server; студент работает внутри |
| `seed.py` | ИСУ → параметры варианта (открытая механика) |
| `Makefile` | `seed` / `check` / `evidence` / `grade` / `clean` |
| `manifests/` | студент кладёт свои YAML (решений нет) |
| `checks/lib.sh` | хелперы: kubectl, port-forward, cast_vote, read_count |
| `checks/0*.bats` | контракты заданий (bats) |
| `checks/scorecard.py` | TAP → scorecard.json + решение по воротам |
| `evidence/collect.sh` | снимок состояния → хеш E |
| `defense/questions.py` | персональные вопросы из манифестов |
| `defense/breakfix.py` | сценарии сбоя по `BREAKFIX_ID` |
| `solution/` | [преподаватель] эталон варианта + `render.py`; `make selftest` |

## Требования

Через воркспейс (рекомендуется) — только Docker Desktop ≥ 4 ГБ; остальное внутри образа.
Без воркспейса — `docker`, `kind` ≥ 0.23, `kubectl` ≥ 1.30, `python3` + `pyyaml`, `bats`, `jq`.

## Статус

Контракты всех пяти заданий реализованы (`01_deploy` … `05_rollout`). Эталонное
решение — `solution/` (Deployment+PVC для БД), самопроверка `make selftest ISU=<ису>`.
Схема сверена с актуальным `example-voting-app`: redis-хост `redis`, БД
`postgres:15-alpine` (postgres/postgres), форма POST `/` поле `vote`, vote выводит
«Processed by container ID &lt;hostname&gt;» (используется в проверке балансировки).

End-to-end прогон требует живого Docker-хоста (воркспейс или машина студента):
образы `example-voting-app` собраны под amd64, на Apple Silicon идут через эмуляцию.
Статически проверено: bats-файлы парсятся, эталон рендерится в валидный YAML.
